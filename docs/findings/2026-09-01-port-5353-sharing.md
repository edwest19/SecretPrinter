# Finding: UDP 5353 can be shared with the Windows DNS Client

**Date:** 2026-09-01
**Tool:** `tools/SecretPrinter.Listen`
**Recorded by:** Claude (Anthropic model, Claude Opus 4.5), directed by Edwin West

## Why this was measured

The proxy has to listen for AirPrint queries on the client network. On Windows,
port 5353 is already held by the `Dnscache` service, and often by browsers too.
If the operating system would not deliver multicast to an additional socket on
that port, the whole architecture needed rethinking before any service code was
written.

## Prior state

```
Get-NetUDPEndpoint -LocalPort 5353
```

Showed three bindings: `Dnscache` (svchost, on both `::` and `0.0.0.0`) and
`msedge`. Two processes already sharing the port implied `SO_REUSEADDR` was in
use and that a third binding was likely to succeed.

## Method

```
dotnet run --project tools/SecretPrinter.Listen -- \
  --interface 192.168.1.234 --interface 192.168.12.245 --duration 60
```

Bound `0.0.0.0:5353` with `SO_REUSEADDR` and `ExclusiveAddressUse = false`,
joined `224.0.0.251` on both interfaces, and enabled `IP_PKTINFO`.

## Result

**Binding succeeded.** 21 packets received in 60 seconds.

| Interface | Index | Packets |
| --- | --- | --- |
| Ethernet 2 (Optimum, 192.168.1.234) | 13 | 15 |
| Wi-Fi (T-Mobile, 192.168.12.245) | 11 | 6 |

Arrival interfaces were reported correctly by `IP_PKTINFO` in every case, with
no confusion between the two networks.

### Incidental finding: the failure mode, captured live

A tablet on the Optimum network was observed querying for the printer's
hostname directly:

```
from 192.168.1.204  QUERY  A epson000000.local
```

Nothing on that network answers, so the query fails and the printer never
appears. This is the exact problem the project exists to solve, observed rather
than theorised.

## What this establishes

- Binding UDP 5353 alongside the Windows DNS Client works on this machine.
- Multicast is delivered to the additional socket on both interfaces.
- The arrival interface can be determined reliably, which is what makes
  per-interface behaviour possible (REQ-ADV-015).

## What it does not establish

Whether the process can **send** mDNS responses that clients accept while
another responder holds the same port. Receiving and responding are different
problems. See `2026-09-02-ios-accepts-advertisement.md`.

## Note on binding strategy

The socket binds the wildcard address, not a specific interface address. On
Windows a socket bound to a single unicast address is unreliable for receiving
multicast; recovering the arrival interface from `IP_PKTINFO` is the supported
approach.
