# The probe keeps only a reply from port 5353 to its own question

*Written by Claude (Anthropic model, Claude Opus 5.5) at the direction of Edwin
West, 2026-10-28. Reviewed by a human before merge.*

**Status: built, measured against the code by tests, and run once on the
printer-side network from the development machine; no release carries it. The
probe, `SecretPrinter.Probe`, now keeps a reply only when it was sent from UDP
port 5353 and carries the identifier of the query the probe sent in that round,
as RFC 6762 §6 and §6.7 require (README `REQ-SEC-018`). It prints any other
datagram as ignored, with why, and keeps nothing of it. Until now it kept every
DNS response that reached its socket, from any port and with any identifier;
every release up to `0.5.0` does so. On the network, the printer's two replies
were kept, as they were by the probe before the change. Neither check makes a
reply trustworthy, for the reason under "Security".**

No IPv6 address, hardware address, network name or device name appears in this
finding, and neither does any machine's address on either network or the
printer's host name. The addresses in the tests are made up, from a range set
aside for documentation (RFC 5737).

## Why this was done

[The finding of 2026-10-26 on the lookups](2026-10-26-a-lookup-takes-only-a-multicast-response-from-port-5353.md)
said of the probe that it "asks from a port the operating system chooses, as a
legacy querier under §6.7 by design, and reads the unicast replies that
brings", that it was not changed, and that whether §6's port rule should apply
to a legacy querier was not worked out.
[The finding of 2026-10-27](2026-10-27-the-conflict-check-takes-only-a-multicast-response-from-port-5353.md)
carried it under "Raised, not decided", and the handoff of 2026-10-27 listed it
as the next item for Claude to settle. It was not put to Edwin West as a
choice; he reviews it before the commit.

The probe matters because a release includes it beside the service
(`REQ-DIST-011`), and [docs/operating.md](../operating.md) has whoever
configures the service by hand take the printer's instance names, host name,
port and address from what it prints.

## What RFC 6762 says

RFC 6762 was read on 2026-10-28 through a fetch tool, which returns text as
short quotations; the passages below are joined from them, in order, with
nothing between them left out.

§5.1, One-Shot Multicast DNS Queries: "The most basic kind of Multicast DNS
client may simply send standard DNS queries blindly to 224.0.0.251:5353";
"These queries are typically done using a high-numbered ephemeral UDP source
port, but regardless of whether they are sent from a dynamic port or from a
fixed port, these queries MUST NOT be sent using UDP source port 5353, since
using UDP source port 5353 signals the presence of a fully compliant Multicast
DNS querier"; and "Typically, the timeout would also be shortened to two or
three seconds."

§6.7, Legacy Unicast Responses: "If the source UDP port in a received
Multicast DNS query is not port 5353, this indicates that the querier
originating the query is a simple resolver such as described in Section 5.1
... In this case, the Multicast DNS responder MUST send a UDP response directly
back to the querier, via unicast, to the query packet's source IP address and
port. This unicast response MUST be a conventional unicast response as would be
generated by a conventional Unicast DNS server; for example, it MUST repeat the
query ID and the question given in the query message."

§6, Responding: "The source UDP port in all Multicast DNS responses MUST be
5353 (the well-known port assigned to mDNS). Multicast DNS implementations MUST
silently ignore any Multicast DNS responses they receive where the source UDP
port is not 5353." And later in the same section: "A Multicast DNS querier MUST
only accept unicast responses if they answer a recently sent query (e.g., sent
within the last two seconds) that explicitly requested unicast responses. A
Multicast DNS querier MUST silently ignore all other unicast responses."

## Whether the two rules apply to the probe

- **The probe is the querier of §5.1.** It opens one IPv4 socket on a port the
  operating system chooses and sends its questions to 224.0.0.251:5353, so a
  responder that follows §6.7 answers it by unicast, to that port.
- **The port rule.** §6 binds "Multicast DNS implementations". It does not say
  in so many words whether a one-shot querier is one. Claude took it that the
  rule applies, because the sentence before it says the source port of *all*
  Multicast DNS responses must be 5353, and §6.7 makes no exception for a
  legacy unicast response. A responder that follows the RFC never answers the
  probe from another port, so the rule loses no answer from one.
- **The rule on unicast responses.** Every question the probe asks sets the
  unicast-response bit (`requestUnicastResponse: true` in each of its three
  rounds), so its queries explicitly request unicast responses whatever else
  is said of a legacy query. §6.7's "MUST repeat the query ID" is what lets the
  probe tell whether a reply answers the query it just sent: each round's query
  has its own identifier, chosen at random.
- **"Recently sent".** The probe listens in each round for the time `--timeout`
  gives, 5 seconds unless set. §6 gives "within the last two seconds" as an
  example, and §5.1 says a simple resolver's timeout would "typically" be two or
  three seconds. Neither is a rule, and the timeout was not changed.
- **"Silently".** The probe still prints a line for what it ignores. Claude's
  reading is that "silently ignore" means nothing is sent back and nothing is
  kept; the probe is a diagnostic, and its own rule, written beside its handling
  of a malformed reply, is "Report rather than hide". The RFC does not define
  the word, so this is a reading, stated as one.

## What the probe did, and what it does now

Until now `QueryAsync` in `tools/SecretPrinter.Probe/Program.cs` took every
datagram that reached the socket, read it as DNS, passed over a query, and kept
every response, whatever port it came from and whatever identifier it carried.
A kept response was printed in the report, and the names in it chose the next
round's questions: round 1's PTR targets became round 2's instances, and round
2's SRV targets round 3's host names.

Now `QueryAsync` hands every datagram to one method, `Program.Judge`, with the
identifier the round's query was built with, and keeps or prints what it says.
`Judge`:

1. Ignores a datagram from any port but 5353, without reading it, and returns
   the line `[round N] … bytes from <address> port <port>: ignored, not sent
   from port 5353 (RFC 6762 s6).`
2. Reads it. A datagram that cannot be read is printed as `unparseable`, as
   before.
3. Passes over a query without a line, as before.
4. Ignores a response whose identifier is not the round's, with the line
   `[round N] … bytes from <address>: ignored, query ID <id> is not this
   round's, <id> (RFC 6762 s6, s6.7).`
5. Keeps anything else, with the line it always had.

Nothing is sent back in any case; the probe sends nothing but its questions.

## Security

The two checks follow the RFC. They do not make a reply trustworthy. The probe
sends its query, identifier included, to the mDNS group, so every device on the
printer-side network receives it, and any of them can answer from port 5353
with that identifier, naming what it likes. mDNS gives no way to tell a printer
from a device answering as one. What the checks stop is a reply that is not,
under the protocol, an answer to the question the probe has just asked: one from
another port, a late answer to an earlier round, or one carrying any other
identifier.

Whoever configures the service by hand from the probe's report measures the
printer's certificate with a separate command, and is told to stop if the
certificate's subject does not name their printer (docs/operating.md). Print
jobs go only to a printer whose certificate matches that fingerprint
(`REQ-SEC-013`). Neither is changed here.

## The tests

`tests/SecretPrinter.Service.Tests/ProbeRepliesTests.cs`, new: eight tests,
each marked `REQ-SEC-018`, calling `Program.Judge` with datagrams built by the
repository's own `DnsResponseBuilder` and `DnsQueryBuilder`, from a made-up
address. The probe's project file gives `SecretPrinter.Service.Tests`, which
already referenced it, sight of its internal types, so that the test can call
`Judge`. No socket is opened.

They were written first and run against the probe with the decision moved into
`Judge` and nothing else changed: the same reading, passing over and keeping as
before, and the identifier passed in but not used. Claude predicted that the
five tests that a datagram is not kept, or is printed as ignored, would fail,
and the three controls pass. That held.

| Test | Before the change | After |
| --- | --- | --- |
| An answer from port 5353 carrying the round's identifier is kept | passed (control) | passed |
| A malformed datagram from port 5353 is printed as unparseable and not kept | passed (control) | passed |
| A query from port 5353 is neither kept nor printed | passed (control) | passed |
| A reply from any port but 5353 is not kept, whatever its identifier (ports 1, 53, 5352, 5354, 49152, 65535) | failed | passed |
| A reply from another port is printed as ignored, with its port | failed | passed |
| A malformed datagram from another port is ignored for its port, not read | failed | passed |
| A reply from port 5353 carrying another identifier is not kept (identifiers 0, one below, one above, 65535) | failed | passed |
| A reply carrying another identifier is printed as ignored, with that identifier | failed | passed |

## What this shows

1. **A reply that does not come from port 5353, or does not carry the round's
   identifier, is not kept, and is printed as ignored** (`REQ-SEC-018`), in the
   tests.
2. **The printer's answers to the probe come from port 5353 and carry the
   identifier of the query they answer.** The changed probe kept both of its
   replies and ignored nothing. One printer, one run, two replies.
3. **The receive loop passes `Judge` the identifier the round's query was built
   with,** for these two replies: had it passed any other, the printer's replies
   would have been printed as ignored.
4. **The change cost nothing here:** the report was the same as without it.

## What this does not show

- That a reply from another port, or with another identifier, is ignored on a
  network. None arrived; only the tests show it.
- Anything about a forged reply that follows the protocol: see "Security".
- A run from a release folder, on FIOS-STB-01, or on any other printer.
- Anything over IPv6. The probe asks over IPv4 only.
- Why steps 1 and 2 got nothing, beyond what Edwin said: that the printer
  network was not up on the development machine.

## Also seen

- Every TTL the report shows for the printer's records is 10 seconds. §6.7 says
  "The resource record TTL given in a legacy unicast response SHOULD NOT be
  greater than ten seconds". The service's own lookups, which the printer
  answers by multicast, log a lifetime of 120 seconds for the same services
  ([the finding of 2026-10-27](2026-10-27-the-build-of-0b51fcc-was-installed-on-fios-stb-01.md)).
  Seen in both runs; not looked into further.
- The report says `TXT (not received)` under `_ipps._tcp.local` in both runs,
  with and without the change. Not looked into.
